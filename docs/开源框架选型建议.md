# 开源框架选型建议

> 结论先行：**以 RuoYi-Vue-Pro（芋道，MIT）作为 ERP 业务基座，Spring AI Alibaba / LangChain4j 做智能体编排，单体优先、后续再拆 yudao-cloud**。如果团队以 Python 为主、且能接受 GPL-3.0，则选 **ERPNext + LangGraph**。

- 版本：v1.0
- 日期：2026-11-24
- 适用项目：AI 原生 ERP 智能体平台（本仓库 PRD v2.0 / 开发方案 v2.0）
- 数据口径：GitHub API，2026-11-24

---

## 1. 为什么不是“从零自研”

本项目的难点不在页面，而在四件事同时成立：

1. **事务正确**：订单 → 锁库存 → 出货 → 开票，状态机与库存不能错；
2. **权限正确**：角色、数据范围、仓库范围、字段级脱敏；
3. **审批正确**：金额/新客户触发审批，不能自批，审批后自动执行；
4. **AI 可控**：模型只能通过工具改业务，所有写操作要草案、确认、审批、审计。

从零自研这四层，演示能跑，但生产化周期和风险不可控。更稳的路径是：**成熟 ERP 基座承接 1–3，团队把精力放在 4 和行业差异化上**。

## 2. 候选对比：ERP 基座

| 项目 | Stars | 许可证 | 技术栈 | 适合本项目的点 | 主要风险 |
| --- | ---: | --- | --- | --- | --- |
| [RuoYi-Vue-Pro（芋道）](https://github.com/YunaiV/ruoyi-vue-pro) | 40.6k | MIT | Java / Spring Boot 3 / Vue3 | RBAC、数据权限、多租户、Flowable 工作流、ERP/CRM/MES 模块、代码生成、国内文档与生态 | 代码量大，需要裁剪；AI 能力需自建/集成 |
| [yudao-cloud](https://github.com/YunaiV/yudao-cloud) | 19.8k | MIT | Spring Cloud Alibaba | 微服务版，适合多团队、规模化 | 初期复杂度高，demo 阶段不建议 |
| [ERPNext](https://github.com/frappe/erpnext) | 41.6k | GPL-3.0 | Python / Frappe / MariaDB | ERP 领域完整，DocType、Workflow、角色权限、Version 审计、REST API | GPL-3.0 商用分发需评估；Frappe 学习曲线；国内实施资源少 |
| [Odoo](https://github.com/odoo/odoo) | 56.1k | 社区版 LGPL-3.0 + 企业版闭源 | Python / PostgreSQL | 应用生态最大，财务/制造/电商覆盖广 | open-core，企业版收费；二开与升级成本高 |
| [JeecgBoot](https://github.com/jeecgboot/JeecgBoot) | 48.6k | Apache-2.0 | Java / Vue3 | 低代码、代码生成快，国内使用广 | 低代码强，ERP 事务内核仍需自建 |
| [NocoBase](https://github.com/nocobase/nocobase) | 25.0k | 开源核心 + 商业插件 | TypeScript | 低代码搭内部系统快，AI 友好 | 不是完整 ERP，复杂事务/库存/审批需大量自建 |
| [Apache OFBiz](https://github.com/apache/ofbiz-framework) | 1.2k | Apache-2.0 | Java | 老牌 ERP，领域模型完整 | 社区小、界面与体验旧、招人难 |
| [Tryton](https://github.com/tryton/tryton) | 0.2k | GPL-3.0 | Python | 轻量、模块化 | 生态小，国内资料少 |

> Stars 只作活跃度参考，不代表质量；许可证以各仓库 LICENSE 与官方说明为准。

### 2.1 结论

- **要“稳”且团队是 Java/国内交付**：选 **RuoYi-Vue-Pro**，它是本项目最匹配的基座。
- **要 ERP 领域深度、团队是 Python**：选 **ERPNext**，但先过法务的 GPL-3.0 评估。
- **低代码平台**（JeecgBoot / NocoBase）适合做外围管理台，不适合直接当 ERP 事务内核。
- **Odoo** 功能最全，但 open-core 边界、企业版授权和升级成本，对“从 0 到 1 的演示型项目”不够稳。

## 3. 候选对比：AI 编排层

| 项目 | Stars | 许可证 | 定位 | 在本项目中的用法 |
| --- | ---: | --- | --- | --- |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 45.4k | MIT | 有状态 Agent 图、人工介入、持久化 | Python 团队的 Agent 状态机：意图 → 工具 → 确认 → 审批 → 回放 |
| [Spring AI](https://github.com/spring-projects/spring-ai) | 9.7k | Apache-2.0 | Java LLM 抽象、Tool Calling、RAG | Java 单体里直接做工具调用与模型网关适配 |
| [LangChain4j](https://github.com/langchain4j/langchain4j) | 13.4k | Apache-2.0 | Java LLM 框架 | 与 Spring Boot 集成，支持 OpenAI 兼容模型（DeepSeek 等） |
| [Spring AI Alibaba](https://github.com/alibaba/spring-ai-alibaba) | 11.2k | Apache-2.0 | 阿里系模型/Agent 编排 | 国内模型（通义/百炼）与工具编排，中文文档友好 |
| [Dify](https://github.com/langgenius/dify) | 161.8k | 开源版 + 商业条款 | 低代码 LLM 应用 / RAG / 工作流 | 做知识库、运营侧 Agent；不建议承载交易写操作 |
| [n8n](https://github.com/n8n-io/n8n) | 211.9k | Sustainable Use License（fair-code） | 集成自动化 | 做通知、同步、周边系统集成，不是 Agent 推理内核 |

### 3.1 结论

- **Java 单体方案**：Spring AI Alibaba 或 LangChain4j，工具调用直接复用 ERP 的 Service，权限与事务在同一进程内，最稳。
- **Python 方案**：LangGraph 做 Agent 编排，ERPNext 通过 REST / MCP 暴露工具；`frappe-mcp-server` 可复用（[PyPI](https://pypi.org/project/frappe-mcp-server/)）。
- **Dify / n8n** 放在外围：知识库、通知、同步；不要让它们直接写核心单据。

## 4. 推荐架构（首选方案）

```text
Vue3 管理端（yudao-ui-admin-vue3）
        │
        ▼
Spring Boot 单体（ruoyi-vue-pro）
├─ 认证 / RBAC / 数据权限 / 多租户
├─ 客户 / 商品 / 订单 / 库存 / 入库 / 出货 / 发票
├─ Flowable：订单审核、开票审批、人工确认
├─ 审计事件表（前序哈希链）+ 回放
└─ 工具 API（OpenAPI / Function Calling）
        │
        ▼
Agent 编排（Spring AI Alibaba / LangChain4j）
├─ 意图识别 → 工具选择 → 参数校验
├─ 草案（Draft）→ 用户确认 → 审批 → 执行
├─ 风险规则（金额/新客户/价格偏离/信用）
└─ 全过程 Trace ID
        │
        ▼
模型网关（OpenAI 兼容：DeepSeek / Qwen / 豆包等）
        │
        ▼
MySQL / Redis / MinIO
```

### 4.1 四条硬约束

1. **Agent 不直连数据库**：只调工具 API，工具内部再做数据范围校验。
2. **写操作三段式**：草案 → 确认 → 执行；高风险再进审批。
3. **幂等**：`action_id` 作为幂等键，重复确认返回首次结果。
4. **可回放**：每次工具调用写审计事件，事件带前序哈希，能还原“谁在什么权限下做了什么”。

## 5. 与现有原型的映射

| 原型能力 | 落地位置（RuoYi-Vue-Pro） |
| --- | --- |
| 角色 / 数据范围 / 仓库范围 | 系统管理 → 角色、数据权限；业务表加 `region` / `warehouse` 过滤 |
| 订单状态机 | 订单表 + 状态机服务；禁止跨状态操作 |
| 金额阈值 / 新客户审批 | 风险规则表 + Flowable 流程定义 |
| 审批中心 | Flowable 待办 + 业务审批单 |
| 审计回放 | 业务事件表 + 哈希链；前端时间轴 |
| 工具配置 / 启停 | 工具注册表 + 权限点；Agent 调用前校验 |
| 外部 ERP 接入 | 适配层（REST/OpenAPI）+ 连接配置 + 连通性测试 |
| AI 工作台 | Vue3 页面 + SSE/WebSocket；卡片渲染复用现有交互 |

## 6. 落地路线（建议 8–12 周）

| 阶段 | 目标 | 产出 |
| --- | --- | --- |
| P0（已完成） | 交互与规则验证 | 本仓库高保真原型 + PRD/开发方案 v2.0 |
| P1（2 周） | 搭基座 | RuoYi-Vue-Pro 单体跑通，账号/角色/数据权限/菜单 |
| P2（3 周） | 迁业务 | 客户、商品、订单、库存、入库、出货、发票 |
| P3（2 周） | 接审批与审计 | Flowable 审批、事件表、哈希链、回放 |
| P4（2–3 周） | 接 Agent | 工具 API、草案/确认、风险规则、Trace |
| P5（1–2 周） | 接模型与评测 | 模型网关、提示词、评测集、越权/注入测试 |
| P6（按需） | 规模化 | 拆 yudao-cloud、多租户、可观测性 |

## 7. 许可证与风险提示

- **MIT / Apache-2.0**：商用友好，保留版权与许可声明即可；仍需注意仓库内第三方依赖。
- **GPL-3.0（ERPNext / Tryton）**：分发修改版或衍生作品时可能触发开源义务；SaaS 使用是否构成分发，需法务按具体部署判断。
- **Odoo**：社区版 LGPL-3.0，企业版为闭源商业授权；上线前确认所用模块的授权边界。
- **Dify / n8n / NocoBase**：开源版附带商业条款或 fair-code 限制，商用前核对官方 LICENSE 与插件授权。
- 本文是技术选型建议，**不构成法律意见**。
